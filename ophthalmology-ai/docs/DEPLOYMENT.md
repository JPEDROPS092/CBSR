# Deployment

## Topology

```
            ┌──────────┐        ┌───────────┐
 clients →  │  ingress │  TLS   │    API    │ ── PostgreSQL
            │  (nginx) │ ─────► │ (uvicorn) │ ── Redis ──┐
            └──────────┘        └───────────┘ ── S3/MinIO│
                                                          ▼
                                                 ┌────────────────┐
                                                 │ inference      │
                                                 │ worker (Celery)│ ── GPU
                                                 └────────────────┘
```

The API is stateless: scale it horizontally. Workers are where the models live;
scale them per device.

## Docker Compose (development / small single-site)

```bash
cp .env.example .env      # set JWT_SECRET and the storage credentials
docker compose up --build
docker compose exec api python scripts/seed_admin.py --email admin@clinic.org --name Admin
docker compose --profile tools up -d flower       # queue dashboard on :5555
```

Services: `api`, `worker`, `postgres`, `redis`, `minio` (+ `minio-init`,
`flower`). The API container runs `alembic upgrade head` before starting.

The compose file's credentials are development defaults. Replace all of them
before exposing the stack to anything.

## GPU workers

```bash
docker build -f Dockerfile.gpu -t ophthalmology-ai:gpu .
docker run --gpus all --env-file .env \
  -v $PWD/models:/app/models:ro ophthalmology-ai:gpu
```

In compose, point the `worker` service at `Dockerfile.gpu` and reserve a device:

```yaml
    deploy:
      resources:
        reservations:
          devices: [{driver: nvidia, count: 1, capabilities: [gpu]}]
```

Guidelines:

* **One worker process per GPU** (`-c 1`). Two processes on one device
  serialize on it anyway and double VRAM use.
* `DEVICE=auto` uses CUDA when available and falls back to CPU with a warning
  rather than failing.
* `INFERENCE_PRECISION=fp16` roughly halves VRAM on supported GPUs; the
  platform downgrades an unsupported request (bf16 without Ampere, fp16 on CPU)
  instead of failing mid-inference. Validate model outputs after changing
  precision — it is a numerical change, not just a speed knob.
* Mount `models/` read-only. Weights are never baked into an image: they are
  large and frequently carry licences that forbid redistribution.
* Call `models.warm_up` at worker start to load checkpoints before the first
  real request.

## Configuration

Every setting is an environment variable; see `.env.example`. The ones that
matter most in production:

| Variable | Production value |
|---|---|
| `ENVIRONMENT` | `production` — enables the startup guards |
| `JWT_SECRET` | ≥32 random characters; the app refuses the dev default |
| `DATABASE_URL` | `postgresql+psycopg://…` |
| `STORAGE_BACKEND` | `s3` — `local` is refused outside local/test |
| `TASK_QUEUE_BACKEND` | `celery` |
| `MODEL_DIR` | mounted volume holding checkpoints + manifests |
| `DEVICE` | `auto` or `cuda` |
| `CORS_ORIGINS` | explicit list, never `*` |
| `LOG_FORMAT` | `json` |

## Migrations

```bash
alembic upgrade head                       # apply
alembic revision --autogenerate -m "…"     # after changing app/database/models.py
alembic downgrade -1                       # roll back one revision
alembic upgrade head --sql                 # review the SQL first
```

Run migrations as a deploy step (a job or the API's start command), never from
two replicas at once. Review autogenerated migrations before committing them —
autogenerate detects added/dropped objects reliably and column changes less so.

## Installing models

```bash
cp layers_unet.pt models/oct/
cp oct_retinal_layers_v1.json models/oct/            # see docs/MODEL_REGISTRY.md
curl -X POST https://…/api/v1/models/refresh -H "Authorization: Bearer <admin>"
```

`POST /models/refresh` re-scans `MODEL_DIR` and syncs the catalogue without a
restart. In a multi-replica deployment, either roll the pods or call it on each
replica: the registry lives in process memory. `python scripts/sync_models.py`
does the same offline.

Verify with `GET /api/v1/models/{model_id}` that the model reports
`available: true` before routing work to it.

## Scaling

| Symptom | Action |
|---|---|
| Slow HTTP under load | add API replicas (stateless) |
| Analyses queue up | add workers; one per GPU, or CPU workers for the built-in models |
| Uploads slow | check object-storage latency; consider presigned direct uploads |
| Database contention | PgBouncer, read replicas for reporting queries |

Queue depth (Flower or Redis `LLEN`) is the signal for worker scaling;
`processing_time_ms` per `ModelRun` shows which model is the cost.

## Observability

Logs are structured JSON with `request_id`, `analysis_id`, `model_id` and
`user_id`. Ship them to Loki/ELK/Cloud Logging and index those fields — that is
what makes an inference traceable from an HTTP call to a model run.

Useful queries: `analysis_completed` by hour, `model_run_completed` p95 of
`processing_time_ms` by `model_id`, `quality_gate_rejected` rate by device
(a rising rejection rate usually means an acquisition problem, not a software
one), `model_run_failed` by `model_id`.

Prometheus/OpenTelemetry/Sentry are not wired in: add an ASGI instrumentation
middleware and a Celery instrumentor at the edges — the correlation ids and
timings they need are already produced.

`GET /health` reports database, storage, registry counts and device profile;
it returns `degraded` instead of failing when a dependency is down.

## Backups

* **PostgreSQL** — `pg_dump`/WAL archiving; this is the system of record for
  results and the audit trail.
* **Object storage** — versioning plus lifecycle rules; masks and reports are
  reproducible from the source image, but the source images are not.
* **`MODEL_DIR`** — back up checkpoints and manifests together. A result is only
  reproducible if the exact checkpoint that produced it still exists.
* Test restores. An untested backup is a hypothesis.

## Production checklist

- [ ] TLS terminated at the ingress; API not directly exposed
- [ ] `JWT_SECRET` generated per environment and stored in a secret manager
- [ ] `ENVIRONMENT=production`, `STORAGE_BACKEND=s3`, `LOG_FORMAT=json`
- [ ] Database and object storage encrypted at rest; backups tested
- [ ] `CORS_ORIGINS` restricted; rate limits sized for real traffic
- [ ] Admin created with a strong password; default accounts removed
- [ ] Model licences reviewed and recorded (`docs/MODEL_LICENSES.md`)
- [ ] Quality-gate thresholds calibrated for the site's cameras
- [ ] Log shipping and alerting on `model_run_failed` / `analysis_failed`
- [ ] Purge job for patient deletion covering object storage
- [ ] Clinical governance: who reads results, and under whose responsibility
